# Техническая спецификация — «Рекомендованный маршрут»

Основание: [Feature Vision — Рекомендованный маршрут](Feature_Vision_Recommended_Route.md). Этот документ описывает реализацию первой версии, а не меняет продуктовые правила vision-документа.

## 1. Область реализации

Маршрут — фиксированный для всех пользователей каталог из **30 остановок**: 20 уроков, 5 кейсов безопасности и 5 исторических сценариев Market Replay. Порядок и ID берутся из раздела 5 vision-документа; отдельный алгоритм персонализации не нужен. Пользовательские данные маршрута не хранятся отдельно: состояние вычисляется из существующего прогресса на сервере.

Уроки идут по главам строго в порядке **Криптовалюты → Blockchain → Финансовые основы → Россия и право** и внутри каждой главы — по учебному порядку 1–5. Кейсы и практика могут стоять между уроками текущей главы. Внутри маршрута нельзя перейти к следующей остановке, пока не завершена предыдущая; свободный доступ к содержимому через существующие разделы приложения сохраняется. Таким образом, блокировка следующей главы относится именно к маршруту, а не ко всему приложению.

## 2. Существующие точки интеграции

| Источник | Что используется | Текущее место в коде |
| --- | --- | --- |
| Уроки | `ProgressRepository.getSnapshot(userId, displayName).completedLessonIds`; урок завершён после успешного итогового теста с порогом 67% | `apps/api/src/persistence.ts`, `apps/api/src/data.ts` |
| Кейсы | `SecurityRepository.getCompletedCaseIds(userId)`; отправка любого ответа завершает кейс | `apps/api/src/security-persistence.ts`, `apps/api/src/security-data.ts` |
| Практика | `SimulationRepository.listCompleted(userId)`; для зачёта нужен завершённый сценарий с сохранённым результатом | `apps/api/src/simulation-persistence.ts`, `apps/api/src/simulation.ts` |
| Профиль и навигация | карточка в профиле, новый экран `/route`, переходы в существующие страницы контента | `apps/web/src/ProfilePage.tsx`, `apps/web/src/App.tsx` |
| Клиентский API | один запрос за состоянием маршрута | `apps/web/src/api.ts`, `apps/web/src/types.ts` |

API уже определяет пользователя по MAX-сессии или гостевой сессии. Новый endpoint должен использовать тот же `requestUser(response)`, что и `/api/v1/profile`; идентификатор пользователя нельзя принимать из URL или тела запроса. Проверка `initData` остаётся в существующем механизме авторизации, а не переносится на клиент маршрута.

## 3. Каталог остановок

Создать серверный модуль каталога, например `apps/api/src/route-catalog.ts`. Его структура — неизменяемый массив с явной версией `1`. Каждая запись содержит:

```ts
type RouteStopDefinition = {
  id: string; // стабильный ID остановки, например "lesson:crypto-intro"
  type: "LESSON" | "SECURITY_CASE" | "REPLAY";
  contentId: string; // ID существующего урока, кейса или сценария
  title: string;
  chapter: "crypto-basics" | "blockchain" | "finance" | "law-russia";
};
```

Позиция в массиве задаёт номер остановки, поэтому отдельное редактируемое поле `order` не нужно. Для промежуточного кейса или сценария `chapter` обозначает учебный участок дороги, внутри которого он расположен. Каталог не копирует текст уроков и не содержит результатов пользователя. При запуске тесты проверяют ровно 30 уникальных пар `type + contentId`, состав 20/5/5, существование всех ID в текущих каталогах, порядок уроков и глав, а также хронологический порядок пяти сценариев. Если состав контента меняется, исправляется каталог и повышается его версия; нельзя молча показывать битую остановку.

## 4. Вычисление прогресса

Добавить серверную функцию, например `getRecommendedRoute(currentUser)`, которая параллельно получает три набора завершений из существующих репозиториев. Новых таблиц и записей в БД для первой версии нет.

Для каждой остановки `completed` вычисляется по её типу:

- `LESSON`: `contentId` присутствует в `completedLessonIds`; простое открытие урока и неуспешный тест не засчитываются.
- `SECURITY_CASE`: `contentId` присутствует в `getCompletedCaseIds`; рискованный ответ тоже засчитывается после получения разбора.
- `REPLAY`: среди результатов `listCompleted` есть хотя бы одна запись с тем же `scenarioId`; несколько завершённых сессий не увеличивают счётчик дважды. `ACTIVE` и `PAUSED` не засчитываются.

`currentIndex` — индекс первой незавершённой остановки. Если такой нет, маршрут завершён, а `currentIndex = null`. `completedCount` — количество завершённых остановок во всём списке. `continuousCompletedCount` — длина непрерывной цепочки завершённых остановок от начала. Дорога окрашивается по `continuousCompletedCount`, а счётчик показывает `completedCount из 30`; эти значения могут различаться, если контент был пройден вне маршрута.

На карте интерактивна текущая остановка и любая уже завершённая остановка для повтора. Незавершённые остановки после `currentIndex` видны, но не открываются из карты. Состояние вычисляется заново при каждом запросе, поэтому прохождение контента вне маршрута не требует синхронизации отдельной сущности. Повторное прохождение не сбрасывает зачёт.

## 5. Контракт API

Добавить `GET /api/v1/route` в существующий Express API. Ответ не кэшируется между пользователями (`Cache-Control: no-store`). Отдельный `POST /route/complete` **не нужен**: завершение фиксируют существующие endpoints теста, кейса и симуляции.

```json
{
  "version": 1,
  "total": 30,
  "completedCount": 2,
  "continuousCompletedCount": 1,
  "currentIndex": 1,
  "finished": false,
  "stops": [
    { "id": "lesson:crypto-intro", "number": 1, "type": "LESSON", "contentId": "crypto-intro", "title": "Что такое криптовалюта", "chapter": "crypto-basics", "completed": true, "available": true },
    { "id": "case:fake-support-seed", "number": 2, "type": "SECURITY_CASE", "contentId": "fake-support-seed", "title": "Поддержка просит фразу восстановления", "chapter": "crypto-basics", "completed": false, "available": true }
  ]
}
```

В реальном ответе `stops` всегда содержит все 30 записей. `available = completed || index === currentIndex`; для полностью завершённого маршрута все остановки доступны повторно. `number` начинается с 1, `currentIndex` — с 0. Никакого `userId` в ответе не требуется. Ошибки чтения прогресса возвращают обычную серверную ошибку, а клиент показывает повторную попытку, не подменяя её нулевым прогрессом.

## 6. Клиентский поток

1. После блока учебного прогресса в профиле разместить карточку-ссылку «Рекомендованный маршрут»: миниатюра дороги, робот, `N из 30` и текущий шаг. Данные брать из `GET /api/v1/route`; загрузка карточки не должна удерживать отображение остального профиля. Если маршрут недоступен, карточка остаётся видимой с действием «Повторить».
2. Новый лениво загружаемый экран `/route` запрашивает тот же endpoint. Вертикальная SVG-дорога, 30 лёгких карточек и четыре заголовка глав рендерятся по данным API. Не добавлять маршрут в нижнюю навигацию.
3. При первом открытии прокрутить к текущему шагу; после ручной прокрутки кнопка «К моему шагу» возвращает к нему. При отсутствии незавершённых шагов показывать финиш. Для анимации подсветки и робота соблюдать `prefers-reduced-motion`.
4. По нажатию доступной остановки перейти на существующий экран: урок — `/lessons/:lessonId`, кейс — `/security/cases/:caseId`, практика — `/practice/:scenarioId`. Параметр `from=route` допустим только как подсказка интерфейсу для кнопки возврата; он не является доказательством прохождения и не влияет на авторизацию.
5. После успешного завершения через существующий поток показывать короткий переход «Остановка пройдена» и действие «Следующая остановка» либо возврат на `/route`. При возвращении повторно запрашивать `/api/v1/route`; не считать остановку завершённой только по факту клика или локальному состоянию.

Если урок, кейс или симуляция прерваны, маршрут остаётся на той же остановке. Для урока и кейса можно вновь открыть существующую страницу; практика переходит на экран сценария и использует доступное в текущем продукте продолжение либо начинает новую сессию. Первая версия не требует отдельного поиска незавершённой сессии по сценарию.

## 7. Крайние случаи и надёжность

- Пользователь прошёл будущую остановку напрямую: её карточка отмечена как завершённая и доступна для повтора, но текущий шаг и зелёная дорога не перескакивают через ранний пропуск.
- Пользователь завершил тест, кейс или сценарий на другом устройстве: при новом запросе виден актуальный серверный прогресс.
- Контент временно недоступен: вместо перехода показывается ошибка и повторная попытка; остановка не отмечается завершённой по ошибке.
- После обновления каталога завершение сопоставляется по `type + contentId`. Перестановка остановок не удаляет историю в существующих таблицах; версия сообщает клиенту, что изменился порядок.
- Для гостя и пользователя MAX применяются одинаковые правила, но прогресс хранится только в рамках его серверной идентичности. Не использовать общий демо-прогресс для разных авторизованных пользователей.

## 8. Минимальные проверки реализации

- Тест каталога: 30 остановок, уникальные ID, состав 20/5/5, корректный порядок четырёх глав и уроков внутри них, существующие `contentId`.
- Тест вычисления: пустой прогресс; непрерывное прохождение; поздняя остановка завершена вне маршрута; повторные сессии одного сценария; незавершённая симуляция; рискованный ответ в кейсе; полностью завершённый маршрут.
- API-тест: данные одного пользователя не попадают другому; endpoint требует действующую сессию при включённом MAX; ошибки источников не превращаются в «0 из 30».
- UI-проверка на телефоне: карточка профиля, длинные названия, обе темы, прокрутка к текущему шагу, доступность остановок, возврат из каждого типа контента, скелетон, ошибка загрузки и уменьшение движения.

Готовность: пользователь может пройти все 30 остановок в заданном порядке, видеть актуальный прогресс без повторного зачёта и не открыть следующую главу **из маршрута** до завершения предыдущей; существующие разделы при этом продолжают работать независимо.
